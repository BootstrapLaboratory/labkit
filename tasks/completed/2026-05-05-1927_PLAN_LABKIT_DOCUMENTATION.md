## Key Findings

Labkit is not a generic helper collection. It is the reusable extraction of
the original app repository's GraphQL server/client runtime constraints.

The original app keeps these boundaries:

- NestJS server owns GraphQL schema generation, resolvers, identity, sessions,
  migrations, Redis-backed pub/sub, and runtime config.
- React/Vite webapp owns routes, Relay operations, UI composition, browser
  auth state, realtime connection state, theme state, and build-time endpoint
  configuration.
- The committed GraphQL schema contract is generated by the server and consumed
  by Relay.
- Browser auth favors memory-only access tokens plus HttpOnly refresh cookies.
- GraphQL WS auth is connection-scoped, so the browser restarts realtime
  clients when auth state changes.
- Redis fanout is needed when GraphQL subscriptions run across multiple server
  instances.
- Apps own product behavior, deployment providers, concrete GraphQL DTOs,
  endpoints, generated Relay operations, CSS/theme values, and product UI.
- Labkit owns reusable constraints: auth contracts, config readers, database
  manifest composition, Nest GraphQL setup, server auth primitives, TypeORM auth
  persistence adapters, browser auth session helpers, Relay transport, realtime
  reconnect policy, external-store mechanics, theme-controller mechanics, and
  Vite build helpers.

The current Labkit website split is good:

- `Docs`: package and concept reference
- `Quick Start`: short path to a working minimal project
- `Tutorial`: guided build-out from project idea to a high-end GraphQL
  server/client application

The current content is only scaffolding and should be replaced with real
documentation.

## Documentation Goals

- Explain what Labkit is for: reusable infrastructure for high-end GraphQL
  server/client web applications, inspired by the original app repository.
- Make ownership boundaries obvious: what Labkit owns and what each consuming
  application must still own.
- Document every public package one by one.
- Provide working code examples that match current Labkit APIs.
- Teach the cross-boundary system, not just individual functions.
- Keep the original app repository as the motivating example, but avoid
  turning Labkit docs into product-specific Anonymous Chat docs.
- Preserve the versioned-docs workflow so published docs can stay aligned with
  npm package versions.

### Quick Start

The `Quick Start` area should be short, command-heavy, and runnable in a new
project. It should not try to explain every design decision.

Decision: Quick Start should begin from the smallest plain Nest/Vite app that
installs Labkit packages. It should not require a Rush workspace.

The opening page should include a short production-workspace note:

- For production monorepos, Rush is recommended.
- The complete reference implementation is deployed at
  `https://bootlab-example-rush-delivery.pages.dev/`.
- The complete reference implementation source is
  `https://github.com/BootstrapLaboratory/typescript_monorepo_nestjs_relay_trunk`.
- Rush Delivery and Rush monorepo integration docs live at
  `https://bootstraplaboratory.github.io/rush-delivery/docs/tutorial/`.
- The official Rush documentation should remain the main source for Rush
  manuals.

Decision: until a separate example repository exists, Quick Start should use
full copy-paste code for the minimal app instead of only small snippets.

Proposed pages:

- `docs/quick-start/README.md`: goal, expected result, prerequisites, and
  package install map.
- `docs/quick-start/server.md`: create minimal Nest GraphQL server with
  Labkit config, GraphQL module, health/bootstrap, CORS, and Date scalar.
- `docs/quick-start/database.md`: add PostgreSQL/TypeORM config with Labkit
  database helpers and one feature database manifest.
- `docs/quick-start/auth.md`: add local auth provider, password hasher,
  access-token signing, refresh-cookie transport, auth resolver, and TypeORM
  adapter.
- `docs/quick-start/webapp.md`: create React/Vite/Relay client with endpoint
  resolution, auth session, auth API, Relay environment, and app providers.
- `docs/quick-start/realtime.md`: add GraphQL WS subscriptions, Labkit
  realtime connection, and Relay subscription network.
- `docs/quick-start/theme.md`: add a minimal theme controller using
  `@omgjs/labkit-webapp-ui`.
- `docs/quick-start/build-and-check.md`: local build/check commands and the
  final shape of the basic app.

The Quick Start target should be a "basic but real" application:

- one Nest GraphQL endpoint
- one query/mutation/subscription path
- optional PostgreSQL-backed auth
- one React page using Relay
- memory access token plus cookie refresh flow
- websocket restart on auth changes
- enough config to extend into a real app

### Tutorial

The `Tutorial` area should teach the system design by building a realistic
GraphQL server/client app. It can link to the original app repository as the
complete reference implementation.

Proposed chapters:

1. `docs/tutorial/README.md`: what we are building, technology map, how Labkit
   reduces duplicate setup, and links to the reference app deployment
   (`https://bootlab-example-rush-delivery.pages.dev/`) and repository
   (`https://github.com/BootstrapLaboratory/typescript_monorepo_nestjs_relay_trunk`).
2. `docs/tutorial/01-system-overview.md`: boundaries between server, webapp,
   GraphQL contract, Labkit packages, app-owned code, docs, and versioning.
3. `docs/tutorial/02-project-foundation.md`: plain project foundation,
   package dependency direction, package-manager choices, and a note that Rush
   is recommended for production monorepos.
4. `docs/tutorial/03-graphql-contract.md`: code-first server schema, committed
   SDL, Relay generation, and why GraphQL is the process boundary.
5. `docs/tutorial/04-server-runtime.md`: Nest/Fastify/Apollo setup, Labkit
   GraphQL helpers, runtime config, structured logging, and GraphQL context.
6. `docs/tutorial/05-database-and-feature-manifests.md`: TypeORM options,
   feature manifests, auth adapter manifest, migrations, and production safety.
7. `docs/tutorial/06-auth-server.md`: identity provider registry, local
   provider, password hasher, access-token claims, refresh-session
   orchestrator, refresh transport, lifecycle events, guards, and roles.
8. `docs/tutorial/07-webapp-runtime.md`: React/Vite providers, endpoint
   resolution, auth session, Relay environment, route preloading, and app
   adapters over Labkit.
9. `docs/tutorial/08-browser-auth-security.md`: memory-only access tokens,
   HttpOnly refresh cookies, session hint, auth-required retry, logout, and
   CORS/path alignment.
10. `docs/tutorial/09-realtime-subscriptions.md`: GraphQL WS params,
    token-change socket restart, reconnect state, user-visible connection
    messages, and Redis fanout.
11. `docs/tutorial/10-ui-and-theme-boundaries.md`: app-owned components and
    design tokens, Labkit class/theme helpers, and why Labkit does not own
    product UI.
12. `docs/tutorial/11-runtime-readiness.md`: build-time endpoint config,
    package formats, validation, migration rules, CORS/cookie alignment, and
    the runtime constraints that matter before deploying with any platform.
13. `docs/tutorial/12-evolving-an-app.md`: add a protected GraphQL feature,
    update schema, update Relay, decide whether behavior belongs in Labkit or
    app code, and choose checks.

The tutorial should reuse the original app's architecture lessons, but examples
should be framed as "your app" unless they are explicitly labeled as reference
implementation examples.

## Generated API Reference Options

No TypeDoc/API Extractor setup exists in Labkit today. The packages already
emit `.d.ts` files, but the docs do not expose generated API reference pages.

Recommended decision path:

1. Start with manual package pages because Labkit needs conceptual ownership
   documentation more than raw symbol listings.
2. Defer TSDoc cleanup unless a manual docs page exposes unclear public API
   naming that should be clarified in source later.
3. Evaluate TypeDoc in a later spike, only when requested:
   - generate per-package API docs from `packages/*/src/index.ts`
   - either commit generated Markdown under `docs/api` or generate into
     ignored Docusaurus input during site build
   - ensure generated pages do not duplicate or replace conceptual package docs
   - decide how generated API pages behave in `docs-versions`
4. Consider API Extractor only if we need formal public API reports,
   compatibility review, or a stricter release gate.

Decision: manual docs first. TypeDoc and generated API reference are out of
scope for the first implementation round.

## Decisions Recorded

- Quick Start starts from a plain Nest/Vite app, not a Rush workspace.
- Quick Start opens with a production note recommending Rush for production
  monorepos and linking to Rush Delivery, official Rush docs, the deployed
  reference app, and the original app repository.
- Quick Start uses full copy-paste code until a separate example repository
  exists.
- The tutorial landing page links to the deployed reference app and the
  original app repository.
- Package pages remain fully manual for the first documentation pass.
- TypeDoc and generated API reference are deferred until explicitly requested.
- Deployment and release-cycle documentation are out of scope for Docs, Quick
  Start, and Tutorial, except for short runtime-readiness notes where Labkit
  behavior depends on deployment inputs such as endpoint config, CORS, cookies,
  package format, migrations, or Redis fanout.
- Production monorepo, Rush Delivery, and full app deployment details should be
  linked out to Rush Delivery, the original app, official Rush docs, README
  material, or `.ai/architecture/deployment` rather than taught in the Labkit
  website.

## Initial Recommendation

Approve a manual-docs-first implementation:

1. Restructure `Docs`, `Quick Start`, and `Tutorial`.
2. Write high-quality conceptual and package docs using current source and the
   original app as reference.
3. Make Quick Start plain Nest/Vite with full copy-paste code, plus a brief
   production note that recommends Rush and links to the reference
   implementation.
4. Keep deployment/release manuals out of the website docs and link to Rush
   Delivery/original app/Rush docs where those topics matter.
5. Defer TypeDoc until after package pages exist and the user asks for an API
